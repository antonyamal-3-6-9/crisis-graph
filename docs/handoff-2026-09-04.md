# CrisisGraph Handoff — Aluva Geospatial Pilot

**Last updated:** 2026-09-04  
**Current baseline commit:** `36c9e3e Initial CrisisGraph emergency routing engine`

## What CrisisGraph is

CrisisGraph is a Rust emergency-logistics and dynamic-routing prototype. It uses:

- Neo4j for the road/shelter operational graph.
- Redis for distributed reservation locks.
- A vLLM-compatible endpoint for SOS triage extraction, with a heuristic fallback.
- Petgraph for deterministic shortest-path calculation.

It is **not offline-only**. Local model serving is a resilience option; real deployments can rely on connected field reports, GIS, GPS/AVL, weather, satellite, and command-centre services.

## Current implementation

The original prototype has a four-stage pipeline:

1. Extract SOS triage and hazards.
2. Reserve shelter capacity and a resource using a Redis lock plus Neo4j mutation.
3. Query passable Neo4j edges and calculate a Petgraph route.
4. Verify basic route endpoints/allocation and produce a tactical brief.

Existing tests pass with:

```bash
cargo test --test integration_tests
```

A small existing compile issue was corrected by adding `#[derive(Clone)]` to `SpatialResolver`.

## Geospatial decisions

The first real-data pilot is:

```text
Name: Aluva–Periyar Emergency Routing Pilot
Centre: Aluva Railway Station
Centre coordinates: latitude 10.10816, longitude 76.35651
Coverage: 10 km radius
Primary hazard: Periyar river flooding / road inundation
Assets: rescue boats, ambulances, evacuation trucks
```

Aluva was chosen because KSDMA documents major Periyar flood impacts in the area and it is a tractable urban/semi-urban road-routing pilot.

## Commands

Regenerate the boundary:

```bash
cargo run --bin generate_boundary -- \
  --name aluva-periyar-pilot \
  --lat 10.10816 --lon 76.35651 \
  --radius-km 10 \
  --output data/boundaries/aluva-periyar-pilot.geojson
```

Download raw OSM road data:

```bash
cargo run --bin download_osm -- \
  --boundary data/boundaries/aluva-periyar-pilot.geojson \
  --output data/raw/osm/aluva-periyar-pilot.osm.json \
  --endpoint https://overpass.kumi.systems/api/interpreter
```

The default endpoint (`https://overpass-api.de/api/interpreter`) did not return data in this environment; the Kumi Overpass mirror succeeded.

## Local-only raw map dataset

The raw map was successfully downloaded locally but is intentionally ignored by Git:

```text
data/raw/osm/aluva-periyar-pilot.osm.json
size: about 16 MB
elements: 117,396
nodes: 104,429
ways: 12,967
relations: 0
```

This is raw OSM JSON, not yet a routable Neo4j graph. It includes vehicle-relevant `highway` ways that intersect the circle and their referenced nodes; ways may extend slightly outside the radius. The later normalizer must apply the precise boundary policy to produced segments.

## Important technical gaps

- The current Petgraph solver uses `UnGraph` (undirected), which is invalid for real OSM roads. Replace it with a directed representation before real routing.
- The current Neo4j seed graph is a demo; do not mix it with imported Aluva data.
- The current verifier does not independently re-check every computed route edge against live Neo4j state.
- Raw OSM map data must be transformed into junctions and directed segments before it can be used by the pipeline.
- OSM turn restrictions require edge-based routing state (or an equivalent representation including the incoming segment), not only junction-to-junction edges.

## Next step

Implement a **normalization/import stage**; do not modify the live pipeline yet.

It should read `data/raw/osm/aluva-periyar-pilot.osm.json` and produce versioned, inspectable staging outputs:

```text
data/processed/aluva-periyar-pilot/
  junctions.geojson
  road_segments.geojson
  import_report.json
```

The normalizer must:

1. Parse OSM nodes and vehicle-eligible road ways.
2. Preserve OSM IDs and tags for provenance.
3. Respect `oneway` and relevant access restrictions.
4. Split roads at topology-changing nodes/intersections.
5. Create directed segments with endpoints, geometry, length, and road properties.
6. Validate no dangling endpoints/duplicate IDs and report counts.
7. Keep this baseline map rebuildable and separate from dynamic flood/blockage overlays.

Do **not** claim production safety or automatic hazard verification. LLM-extracted hazard reports are candidates; verified field/dispatcher events should control route closure.
